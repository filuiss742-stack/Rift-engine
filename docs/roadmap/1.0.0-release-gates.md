# Rift Engine 1.0.0 — Release Gates

## Purpose

Rift Engine 1.0.0 is the first stable, independently usable release of the game constructor. It must let a developer or an unfamiliar AI agent create, run, inspect, validate, and package a real game for Android and Windows without editing engine internals for ordinary gameplay work.

This is a release contract, not a claim that the listed systems already exist.

## Product boundaries

- Primary language and API: Kotlin.
- Release targets: Android and Windows.
- One shared game/runtime model across both targets.
- Modular, composable gameplay; no mandatory genre hierarchy.
- A game may change camera, controls, physics profile, presentation, and gameplay systems between modes while retaining explicitly shared game state.
- Real-time gameplay is supported. Turn-based gameplay may be built by a game, but it is not the engine's only or default combat model.
- 2D and 3D are first-class rendering goals, including a documented path for mixing them in one game.
- No claim of completeness based only on compiling classes or placeholder interfaces.

## Release gates

A gate is complete only when implementation, automated tests, documentation, and a working example exist.

### G1 — Stable runtime and lifecycle

- Fixed-step simulation with explicit frame timing and safe pause/resume.
- Deterministic update ordering and documented thread ownership.
- Safe scene creation, replacement, transitions, and disposal.
- Predictable queued input dispatch.
- Recoverable subsystem failures are isolated; fatal failures are explicit and inspectable.
- No platform-specific imports in the engine core.

### G2 — Scene, entity, and composition model

- Clear ownership and lifecycle for scenes, entities, and components.
- Add/remove/replace operations are safe during update and rendering.
- Transform hierarchy supports position, rotation, scale, and parent-child relationships.
- Entities compose optional capabilities without deep genre-specific inheritance.
- Shared game state can survive scene and mode transitions.

### G3 — Rendering

- 2D primitives, sprites, textures, text, fonts, render layers, transforms, camera viewport, and clipping.
- Sprite animation and atlas support.
- Tilemap or equivalent efficient world composition.
- Basic 3D scene rendering with camera, mesh, material, depth, and lighting on both release targets.
- A documented mixed 2D/3D composition path.
- Platform backends expose the same documented logical rendering contract.
- Resource ownership, disposal, and missing-resource diagnostics are tested.

### G4 — Physics and collision

- 2D body types and collision shapes.
- Broad-phase candidate filtering and narrow-phase collision tests.
- Stable collision response for supported shapes.
- Sensors/triggers, collision layers/masks, overlap queries, and ray/shape queries.
- Gravity, grounded state, and platformer movement derive from actual physics contacts.
- Fixed-step tests cover edge cases; tunneling limitations are documented.

### G5 — Input

- Named actions independent of physical devices.
- Keyboard, mouse, touch, and gamepad bindings where supported.
- Remapping and multiple bindings per action.
- Pointer coordinates convert correctly through viewport and camera transforms.
- Virtual controls for touch games.
- Input state and edge events are testable without a device.

### G6 — Assets and audio

- Stable asset identifiers and a project asset catalog.
- Loading and validation for textures, sprites, fonts, audio, and 3D resources.
- Missing and incompatible assets produce actionable diagnostics.
- Resource caching and explicit disposal.
- Sound effects, music playback, volume controls, and platform-safe audio lifecycle.
- Import and runtime asset behavior is documented for both targets.

### G7 — Reusable gameplay building blocks

- Health, damage, status/effect hooks, and hit detection primitives.
- Interaction targets and interaction queries.
- Inventory/item data primitives and safe save/load integration.
- Quest/objective and branching narrative runtime with a usable presentation example.
- Realtime combat building blocks remain optional and replaceable.
- Top-down and platformer movement profiles.
- These systems are optional capabilities; the core runtime must not become a single RPG framework.

### G8 — UI and game flow

- Reusable UI primitives for panels, labels, buttons, layout, focus, and input.
- Scene transitions with lifecycle guarantees.
- Mode transitions can swap camera, controls, physics, renderer configuration, and gameplay modules without duplicating shared progression.
- Resolution/viewport scaling and safe-area handling for Android.
- Readable text sizing, focus/navigation support, and configurable controls.

### G9 — Project format and AI-native workflow

- Standalone Kotlin game template that builds without depending on the demo game.
- Versioned machine-readable project manifest and schema.
- Manifest validator with stable error codes and precise field paths.
- GAME_AGENT.md as a short entrypoint to project-specific instructions.
- Task-focused API documentation and tested examples.
- Safe change workflow: inspect, plan, validate, patch, test, show diff, rollback.
- Build/test commands and structured results consumable by AI agents.
- Ordinary gameplay tasks use public game APIs; engine changes require a genuine engine-level feature or bug fix.

### G10 — Diagnostics and safety

- Bounded structured diagnostics with stable codes, severity, source/asset/scene/module references, and actionable next steps.
- Distinguish confirmed errors, warnings, and hypotheses.
- Detect known dependency, module, asset, scene, and project-format conflicts.
- Do not claim universal bug detection.
- No silent source rewriting or destructive project changes.
- Optional module failure must not automatically disable unrelated systems.
- Explicit ownership, cleanup, and compatibility validation for extensions.

### G11 — Build, tests, and release

- CI builds Android APK and Windows application image from a clean checkout.
- Unit and integration tests cover each release gate.
- A sample game demonstrates top-down action, side-view platforming, and a mode transition sharing game state.
- The same sample project runs on Android and Windows.
- Windows packaged artifact is manually smoke-tested; CI packaging alone is not proof of launchability.
- Android APK is installed and smoke-tested on a real device.
- Release notes, migration notes, API stability policy, and versioned template are published.
- No gate is complete without evidence.

## AI acceptance test — mandatory release gate

Use a clean model with no prior Rift-specific knowledge. Give it only the template, manifest, GAME_AGENT.md, task-relevant docs, and this task:

> Create a small top-down real-time action RPG. Add player movement using keyboard and virtual touch controls, a short-range action ability, a dodge, and a slime enemy with 30 health that follows the player. When defeated, the slime drops a coin. Add a small HUD showing player health and coin count. The game must run on Android and Windows.

Score each item pass/fail:

1. The clean project builds on the first attempt.
2. The agent discovers and uses real public APIs without inventing methods.
3. The agent does not edit engine internals for ordinary game logic.
4. The requested gameplay works at runtime.
5. Tests cover the new behavior and pass.
6. Diagnostics identify seeded configuration mistakes with actionable messages.
7. The agent presents a scoped diff and does not modify unrelated files.
8. The same project runs on both release targets.

A release candidate must score at least 7/8, with items 2, 3, and 4 mandatory passes. Record model, task, template version, engine commit, target, and test output so the result is reproducible.

## Implementation order

Work in vertical slices. Prefer a small complete feature over a large collection of disconnected APIs.

1. Audit and harden runtime lifecycle, threading, and public API boundaries.
2. Establish project template, manifest format, validator, and GAME_AGENT.md.
3. Deliver 2D transforms, rendering, assets, camera, and animation.
4. Deliver action-based input and a real 2D physics/collision world.
5. Deliver UI, audio, save/load, and reusable gameplay blocks.
6. Deliver mode transitions and a shared-state example game.
7. Deliver minimum 3D rendering and a mixed 2D/3D example on both platforms.
8. Run the AI acceptance test, fix observed failures, and repeat.
9. Perform Android device and Windows packaged-artifact smoke tests.
10. Freeze public APIs, publish migration notes, and tag 1.0.0 only after all gates pass.

## Versioning policy

- 0.x: APIs may change while architecture is being established.
- 1.0.0: documented public APIs and project format are stable under semantic versioning.
- Breaking public API or manifest changes after 1.0 require a major version unless covered by a documented migration path.
- Do not label an unfinished milestone as 1.0.0 merely because the repository version string was changed.
