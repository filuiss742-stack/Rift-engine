# Rift Engine 0.5.0 — First Usable 2D Game Engine

## Purpose

0.5.0 is the first milestone where an independent developer can build and run a small but complete 2D game on Android and Windows using Rift's public Kotlin APIs. It is a development milestone: public APIs may still change before 1.0.0.

This release must be a working engine, not a collection of placeholder interfaces. Every completed gate requires implementation, tests, documentation, and a running example.

## Product scope

- Kotlin-first, shared runtime for Android and Windows.
- 2D-first engine with top-down, side-view/platformer, isometric-style presentation, and custom gameplay modes.
- Real-time gameplay supported; no mandatory turn-based or RPG-specific architecture.
- Shared game state can persist across scenes and gameplay modes.
- Optional gameplay packs are composed through public APIs.
- 3D and mixed 2D/3D are future milestones. 0.5.0 must keep renderer and scene boundaries extensible, but must not claim to ship a 3D renderer.

## Release gates

### G1 — Runtime and lifecycle
- Fixed-step simulation with frame-delta clamping and pause/resume.
- Defined update/render/input thread ownership.
- Safe scene changes, object/component mutation, and disposal.
- Input events are queued and delivered deterministically.
- A failure in one optional module does not silently stop unrelated systems.
- Core has no Android, AWT, or Swing dependencies.

### G2 — Entity and composition
- Scene-owned entities with position, rotation, scale, and clear lifecycle.
- Reusable components with attach/detach/update/render lifecycle.
- Parent-child transforms or a documented alternative for composing moving world objects.
- Shared game-state service that survives scene/mode changes.
- No required genre-specific inheritance tree.

### G3 — 2D rendering
- Primitive and text drawing, alpha blending, transforms, clipping, and render layers.
- Texture/sprite rendering with explicit resource ownership.
- Sprite sheets/atlases and time-based animation.
- Camera viewport, zoom, screen/world coordinate conversion, and screen-space UI.
- Tilemap or equivalent efficient world composition.
- Consistent rendering semantics across Android and Windows.
- Resource disposal and missing-resource diagnostics.

### G4 — 2D physics
- Static, kinematic, and dynamic bodies.
- AABB and at least circle collision shapes.
- Broad phase that scales beyond a handful of objects.
- Collision response, gravity, grounded state, and stable fixed-step behavior.
- Sensors/triggers, layers/masks, overlap queries, raycasts.
- Begin/stay/end contact events or a documented polling contract.
- Tests for high-speed motion, corners, stacked bodies, filters, sensors, and removal during play.
- Tunneling limitations documented; continuous collision detection can remain optional if ordinary gameplay is reliable.

### G5 — Input
- Device-independent named actions.
- Keyboard, mouse, touch, and common gamepad input on supported hosts.
- Pointer press/release/move events, multi-touch identity, and world-coordinate conversion through the camera.
- Multiple bindings, remapping, pressed/released/held state.
- Reusable virtual joystick and buttons for touch games.
- Focus-loss handling that releases stuck keys/buttons.

### G6 — Assets and audio
- Project-relative asset catalog and stable asset IDs.
- Load/validate textures, sprite atlases, fonts, and audio.
- Cache resources, report missing assets, and release platform resources.
- Sound effects and music playback, pause/resume, volume and lifecycle handling.
- Same logical asset API for Android and Windows.

### G7 — UI and gameplay building blocks
- Reusable panels, labels, buttons, image widgets, layout, focus, and input routing.
- Health/damage, hitboxes, interaction, inventory primitives, and status-effect hooks.
- Branching dialogue presentation example, not just headless graph data.
- Optional real-time action-combat building blocks.
- Top-down and platformer movement connected to physics.
- Save/load for structured game state, not only primitive string/float keys.

### G8 — Game flow and modes
- Scene transition API with enter/exit/dispose guarantees.
- Mode changes can replace camera, controls, physics profile, and presentation while retaining shared progression.
- Transition effects are optional and replaceable.
- Example combines at least two gameplay modes without duplicating player progression.

### G9 — Project and AI workflow
- A separate Kotlin game template with its own build files and a versioned engine dependency.
- A game project builds without depending on :demo-game or the engine source tree; remote artifact publication and a one-step bootstrap remain explicit release gates.
- Versioned manifest with schema, module declarations, assets, scenes, and target settings.
- Validator checks manifest paths, declared assets, module relationships, and entrypoint structure where feasible.
- Short GAME_AGENT.md gives an unfamiliar model the exact safe workflow.
- Game-agent changes are restricted to project files by validation; engine/platform internals require explicit human approval.
- Task-specific docs and examples reflect real public APIs.

### G10 — Diagnostics and safety
- Structured, bounded diagnostics with stable codes, severity, source location, and actionable suggestions.
- Distinguish confirmed errors from warnings and hypotheses.
- Detect known module/dependency/asset/manifest conflicts early.
- No silent file rewriting, destructive cleanup, or unreviewed engine modifications.
- Diagnostics must not claim to find every possible bug.

### G11 — Build and acceptance
- Clean-checkout CI builds Android APK and Windows application image.
- Automated tests cover every shipped subsystem and platform adapter.
- Sample game demonstrates top-down real-time gameplay, side-view/platformer mode, and a shared-state transition. The current shared demo uses TAB to switch between modes.
- Same project builds and behaves consistently on Android and Windows.
- Android APK is installed and smoke-tested on a real device.
- Packaged Windows app is launched and smoke-tested.
- Blind AI test: a clean model creates a small playable game using only the template, manifest, GAME_AGENT.md, and task-relevant docs.
- Record engine commit, template version, model, task, targets, test output, and scoped diff.

## Mandatory blind AI task

> Create a small top-down real-time game. Add player movement, an action ability, a dodge, one enemy with health that follows the player, a pickup dropped when the enemy is defeated, and a HUD. Include keyboard and virtual touch controls. Build for Android and Windows.

Pass conditions:
1. Clean project builds without manual repair.
2. The model uses only documented, existing public APIs.
3. It does not edit engine or platform modules for ordinary game logic.
4. Gameplay works at runtime on both targets.
5. Tests cover the requested behavior and pass.
6. A seeded manifest or asset error is diagnosed with a useful code and fix suggestion.
7. The model presents a scoped diff and makes no unrelated/destructive edits.

A 0.5.0 release candidate must pass all seven conditions. A failure is a development task, not something to explain away.

## Explicitly out of scope for 0.5.0

- Full 3D renderer and hybrid 2D/3D scene composition.
- Visual editor and community module marketplace.
- Arbitrary downloaded native plugin binaries.
- Advanced rigid-body simulation, joints, fluid/cloth simulation, and networking.
- Console, Linux, and macOS targets.

These are future directions, not current capabilities.

## Versioning

- 0.5.0 is a usable development milestone; public APIs may still change.
- 0.6–0.9 can add capabilities and refine contracts.
- 1.0.0 requires stable public APIs, migration policy, reproducible template, and all 1.0 release gates.
- Do not create a release tag until all 0.5.0 acceptance evidence exists.
