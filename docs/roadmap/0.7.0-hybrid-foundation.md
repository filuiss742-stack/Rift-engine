# Rift Engine 0.7.0 — Hybrid 3D Foundation Milestone

Status: active development contract. This document describes acceptance criteria; it does not imply that every listed capability is implemented.

## Purpose

0.7.0 establishes a credible, testable hybrid 2D/3D foundation for games that need a real 3D world with 2D characters and UI. It is not a production-ready engine release and does not replace the 1.0.0 release contract.

The milestone must preserve the engine's universal, Kotlin-first, modular design. No requirement in this document may make the engine dependent on the current RPG, its story, its heroine, its assets, or its RTS campaign.

## Product boundaries

- Shared platform-neutral game/runtime logic for Android and Windows.
- 2D remains a first-class renderer and remains usable for games that do not need 3D.
- 3D is a separate rendering capability with a documented shared contract and platform backends.
- Hybrid 2D/3D composition is supported without forcing 2D characters or UI into 3D models.
- Gameplay-specific systems (RPG, RTS, dialogue, quests, inventory, combat) remain optional modules or game code.
- No platform APIs in shared engine core.
- No claims of GPU acceleration, depth correctness, PBR, shadows, model import, physics, or production performance until implemented and tested.

## 0.6.x — 3D rendering and asset foundations

### Rendering contract
- Explicit 3D camera, coordinate, matrix, viewport, clipping, and depth conventions.
- Mesh vertices/indices, UV coordinates, normals, tangents, and validated bounds.
- Materials with explicit texture slots, filtering, wrap modes, alpha mode, and ownership.
- Correct near/far clipping and a depth-correct opaque path.
- Transparent geometry has a documented sorting/blending policy.
- Frustum culling and draw statistics.
- 2D renderer remains independent and regression-tested.

### Asset pipeline
- Stable asset IDs and project-relative paths.
- Import validation for supported image formats and glTF 2.0 / GLB subset.
- Explicit limits and actionable diagnostics for malformed meshes, invalid indices, missing textures, invalid UVs, and unsupported material features.
- No silent texture downscaling or silent material fallback.
- Source assets remain preserved; generated runtime assets are reproducible.

## 0.7.x — Hybrid world foundation

### World composition
- Shared world scene can contain 3D mesh entities, 2D billboard/sprite entities, lights, cameras, and screen-space UI.
- Correct depth testing for opaque meshes and sprite quads, with documented transparency ordering.
- Camera-aware directional sprite view selection with stable ground pivot.
- Animation state and view direction are independent selectors.
- Missing sprite views and animation frames generate actionable diagnostics.
- World transforms are consistent for rendering, interaction, and physics.

### 3D interaction and collision baseline
- Ray queries against registered colliders with layer/mask and distance filtering.
- At minimum: axis-aligned boxes, oriented boxes or documented limitation, spheres, and capsules.
- Broad-phase spatial acceleration; narrow-phase hit results include object identity, distance, point, and normal.
- Render meshes are not implicitly reused as high-cost physics colliders.
- Interaction targets are optional components and remain game-defined.

### Runtime integration
- Lifecycle-safe creation, mutation, and disposal of 3D resources.
- Explicit thread ownership for resource upload and rendering.
- Resource cache and disposal tests.
- Android and Windows use the same logical world and capability declarations.
- A small independent hybrid sample proves the engine can be used outside the RPG project.

## Explicitly not required for 0.7.0

- Full commercial-grade renderer or parity with Unreal/Unity.
- Full PBR feature set, global illumination, advanced shadows, post-processing stack.
- Full rigid-body physics, cloth, fluid, destruction simulation.
- Networking, multiplayer replication, visual editor, marketplace.
- A specific RPG combat system, quest system, or RTS campaign.
- Automatic conversion of arbitrary 2D images into accurate 3D geometry.
- A complete game or production art pack.

These remain optional future work and must not be smuggled into the engine core as game-specific assumptions.

## Mandatory acceptance evidence

A capability is complete only when all applicable evidence exists:

1. Implementation in the correct module with platform-neutral public API.
2. Unit tests for edge cases and invalid input.
3. Platform integration tests for Android and Windows adapters.
4. Documentation with limitations and resource ownership.
5. A runnable sample that uses only documented public APIs.
6. Diagnostics for unsupported or malformed inputs.
7. CI result tied to an exact commit.
8. Manual smoke test for device/packaged behavior where hardware or OS lifecycle matters.

## Architecture protection rules

- Before adding an engine API, search for an existing equivalent and explain why reuse is insufficient.
- Do not add game-specific nouns or assumptions to core abstractions.
- Keep optional features behind capabilities/modules; absence must be explicit and diagnosable.
- Avoid duplicate sources of truth for transforms, time, input, or resource ownership.
- Do not introduce platform dependencies into core to simplify one backend.
- Prefer small vertical slices over disconnected interfaces.
- Breaking changes in 0.x require migration notes and tests.
- Never merge to main or publish a release tag without explicit project approval.

## Current first vertical slice

The first 0.7.0 branch slices currently provide:
- CPU 3D triangles clipped against all six perspective-frustum planes;
- UV interpolation at clipping intersections;
- tests for near-plane crossing, far-plane rejection, and horizontal frustum rejection;
- platform-neutral 3D ray queries against AABB and sphere collider proxies;
- layer-mask filtering, maximum distance, nearest/all-hit sorting, inside-origin exit hits, and collider removal;
- tests for ray positions, normals, filtering, ordering, and lifecycle.

Known limitations remain: the renderer still uses painter sorting rather than a depth buffer, and the 3D query world currently uses a linear scan rather than a spatial broad phase. The 3D query layer is not a rigid-body physics solver.
